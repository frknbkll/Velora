# Velora account security

The account server includes the protections below. Two-factor sign-in is optional until an account owner finishes enrollment; existing accounts are not enrolled automatically.

## Set up two-factor sign-in

1. Start Velora with `Start-Velora.cmd` and sign in.
2. Open **Your account → Account security** (`account.html#security`).
3. Enter your current password and scan the QR code with an authenticator app, or enter its setup key manually.
4. Confirm a current six-digit authenticator code. Save the ten recovery codes, then acknowledge that you saved them.

QR codes are generated by a bundled library in your browser. Setup keys are not sent to an external QR service. Setup expires after ten minutes if it is not confirmed. Neither the QR code nor its setup key is kept in browser storage.

After enrollment, signing in requires the password and an authenticator code or an unused recovery code. A password alone does not create an authenticated session. Verification challenges expire after five minutes and have attempt limits. Authenticator codes change every 30 seconds and cannot be reused after successful verification. Recovery codes work once each.

Disabling two-factor sign-in or replacing recovery codes requires the current password and a valid authenticator or recovery code. Replacing recovery codes invalidates the old set. Codes are displayed only when generated; download them explicitly if you want a copy. Signing out, acknowledging the codes, or leaving the page clears the displayed secrets. Do not use shared screenshots of real enrollment keys or recovery codes.

## Sessions and failed attempts

- **Your devices:** the account security panel lists current sign-in sessions, their browser/device labels, IP addresses, and activity times. Sign out one session or all other sessions. A session can only be managed by its owner.
- **Administrative sessions:** the server expires administrator sessions after 30 minutes without authenticated API activity, and after at most eight hours. “Keep me signed in” does not extend these administrator limits.
- **Customer sessions:** the existing 12-hour expiration, or up to 30 days for a remembered sign-in, remains in place.
- **Sensitive changes:** password and two-factor changes invalidate other sessions and pending sign-in challenges. The current session's token and request-verification token are rotated.
- **Failed sign-ins:** persistent failure limits temporarily block repeated attempts against an email address or from an IP address. Five failed attempts for an email address, or twenty from an IP address, in fifteen minutes trigger blocking. Additional request limits and two-factor challenge limits apply. Restarting the server does not clear persistent failure history.

Session cookies are HttpOnly and SameSite=Lax. Session tokens are random, and their hashes are stored in the database. Credentials, challenges, setup keys and recovery codes are not saved to local storage or session storage by the application. Protected pages recheck authentication when restored through browser history.

## Administrator security center

Open **Admin portal → Security** to review failed sign-ins, blocked attempts, active administrator sessions, and administrator two-factor enrollment. Filter the event list by severity or search account hints, IP addresses and event descriptions.

Events include sign-in successes and failures, access denials, request-verification failures, session revocation, password changes, and two-factor changes. Email hints are masked. Passwords, verification codes, setup keys, recovery codes, session cookies and request bodies are not written to these events. The log retains up to 2,000 events for up to 30 days; the portal displays the latest 100. These records describe application activity rather than an external firewall or intrusion-detection service.

## Department folder access

Owner administrators manage `@velora.com` colleague identities and folder grants in **Admin → Velora accounts**. A public sign-up is always a customer, even when its address uses `@velora.com`; only explicit owner provisioning creates colleague access. Customer accounts stay outside the colleague list. Existing explicitly assigned work-address profiles are retained during migration.

Finance and Human Resources require an enabled Velora profile, matching primary department and explicit Read or Manage permission, or an explicitly assigned **Full control** role. Full control grants owner administration and management of all folders. Store-manager and warehouse roles do not grant this override. The override checks current role, enabled state and Full-control assignment on each file request. Other departmental files require an enabled colleague profile and an explicit grant unless Full control is assigned. Company-library Read access is included for enabled colleagues and administrators; its website originals already belong to the public storefront.

Colleague creation and role changes require an authenticated owner session, matching website origin and CSRF token. Starting passwords use the same password hash as other accounts and do not appear in API responses or security events. Disabling a colleague prevents sign-in and revokes sessions; role changes invalidate existing sessions. Self-demotion and deleting or disabling the last enabled owner are prevented. A work address alone grants no privileges or email-mailbox provisioning.

Private files live beside the database in `shared-folders/`, outside the public media library. Their random storage names are not public URLs. All file operations, including direct download and preview links, check current server-side membership and permissions. Revocation takes effect on the next request without requiring sign-out. File responses use no-store caching and nosniff headers, with attachment downloads and raster-only inline previews. Access changes, denied access, uploads and deletions enter the security event log without file contents.

Back up `shared-folders/` with its matching database and security key while the server is stopped. Account deletion removes membership and grants; department-owned files remain shared with other authorized colleagues.

## Storage and backups

With the default configuration, private account data is in `.velora/velora.sqlite3` and the security master key is in `.velora/security.key`. When using `--database`, the key is stored next to the chosen database. The server derives authenticator secrets using the private master key and a per-account random nonce; plaintext authenticator secrets and recovery codes are not stored in the database.

Back up the matching database and security key together, plus `assets/uploads/` for product photos. Keep backups private. The server checks that its key matches the database and refuses to start if a previously configured key is missing or mismatched. Do not delete the key to try to reset two-factor sign-in. Email-based account recovery is not implemented.

The web server excludes the database, key, backups, Python source and test files from public file serving. Passwords use salted PBKDF2-SHA256 hashes. Server-side role checks protect administrative APIs. Mutations require the matching origin and JSON, and authenticated mutations also require a session-specific CSRF token. Product uploads have type, size, dimension, filename and path checks.

## Hosting boundary

This remains a local development server built on Python's HTTP server. For public hosting, use a maintained production application server and HTTPS, and arrange restricted private storage, backups and operational monitoring. `--secure-cookies` enables Secure cookies and HTTPS-related headers for a deliberately configured HTTPS endpoint; it does not provide TLS itself. Forwarded headers are not trusted automatically.

The included browser policies restrict script sources, framing, cross-origin resource use, and camera/microphone/geolocation access. These protections reduce specific risks; they are not a guarantee against every attack.

## Verification and references

API tests use temporary databases and keys. Browser checks use disposable accounts:

```powershell
python -m unittest discover -s py/tests -p "test_*.py" -v
python py/tests/run-security-browser.py
```

Authenticator behavior follows [RFC 6238](https://www.rfc-editor.org/rfc/rfc6238). Design references include the [OWASP multifactor authentication guidance](https://cheatsheetseries.owasp.org/cheatsheets/Multifactor_Authentication_Cheat_Sheet.html) and [OWASP session management guidance](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html). The bundled [Nayuki QR Code Generator](https://www.nayuki.io/page/qr-code-generator-library) is MIT-licensed; its release URL and SHA-256 are recorded in `json/vendor/qrcodegen-source.json`.
